# WORLDPROOF 黑客松评审指南

> **Build it. Break it. Fix it.**

## 1. WORLDPROOF 黑客松发起目的

南方科技大学（SUSTech）地处粤港澳大湾区的创新之城深圳，以“明德求是，日新自强”为校训。SUSTech-BIO 团队也一直关注合成生物学如何走出实验室、回应真实世界的需求与限制。基于这一理念，团队在南方科技大学发起并主办 WORLDPROOF 黑客松。与常规项目路演相比，WORLDPROOF 不只关注方案是否新颖、展示是否亮眼，更关注它离开实验室后，能否适应真实的使用环境并经得起检验。

参赛团队需在活动前完成约 70% 的可运行 Demo。活动当天上午，各团队先进行一小时的开放摊位交流，展示作品、交换意见，并以 Red Team 身份为其他项目寻找漏洞、提出挑战；这一环节不设评委。收到 New Constraint Card 和其他团队的建议后，参赛者利用余下的制作时间集中修改自己的 Demo。正式评审在下午进行，每支团队通过简短的 PPT，向现场和线上评委展示经过这轮真实世界压力测试后修改完成的 Demo，并说明方案如何回应收到的问题。

评审的核心问题是：

> 团队能否发现项目可能失效的环节，吸收外部批评，并重新设计项目，使其能够负责任地应用于真实世界？

WORLDPROOF 将设计—构建—测试—学习（Design-Build-Test-Learn, DBTL）循环从实验室优化延伸至现实环境，引入利益相关者、基础设施、可及性、治理、不确定性和突发事件等因素。

## 2. 比赛赛道

团队可参加以下两个赛道之一。两个赛道采用相同的评分标准。评分应取决于团队的推理与迭代质量。

### 项目赛道（PROJECT TRACK）

团队可携现有 iGEM 或合成生物学项目参赛。评审不考察项目的生物学新颖性、实验表现、专利潜力或商业计划质量，而是考察团队能否明确真实世界挑战、回应外部反馈，并使最终应用更适合实际使用。

### 场景赛道（SCENARIO TRACK）

团队从主办方提供的虚构场景中选择一个进行设计。这些场景取材于真实新闻和公共议题。团队可围绕场景制作应用程序、决策工具、监测系统、沟通界面、模拟程序或服务原型。

## 3. 评委评审内容

评委只需评审以下两项内容：

团队将在下午的 PPT 展示中呈现 **Change Log** 和 **Final Demo**；评委无需提前查看单独文件。

1. **Change Log**：团队对优先挑战及其回应的记录，必须包括：
   - 主办方发放的 New Constraint Card；
   - 其他团队提出的建议；
   - 团队选择优先处理的一项或多项挑战；
   - 这些挑战为何重要；
   - 团队为此作出的设计决策；
   - 仍未解决的重要问题。
2. **Final Demo**：团队在最终评审中展示的版本。

**评委无需单独查看基线原型（Baseline Demo）或挑战卡（Challenge Cards）。** 主办方可保留这些材料，用于记录活动过程。

| 材料 | 评分用途 |
| --- | --- |
| Change Log | **Challenge / 30** |
| Change Log + Final Demo | **Fix / 45** |
| Final Demo + 团队说明 | **World Readiness / 25** |

## 4. 建议的团队展示安排

上午一小时的摊位环节只用于参赛团队交流和提出 Red Team 挑战，不属于正式评审。正式评审在下午进行，评委包括现场评委和线上评委。每支团队的评审时间建议为 **六分钟**：四分钟 PPT 展示，两分钟评委提问。

| 时间 | 团队展示内容 |
| ---: | --- |
| 30 秒 | 团队名称、参赛赛道、项目或场景，以及目标用户 |
| 60 秒 | 挑战归纳：团队优先处理了哪些限定条件和同伴反馈，为什么？ |
| 120 秒 | Final Demo，以及团队在修改阶段作出的主要设计决策 |
| 30 秒 | 仍然存在的不确定性、限制或暂停/终止条件 |
| 120 秒 | 评委提问 |

团队不应在评审时段内进行完整的 iGEM 项目汇报。如果科学背景占用过多时间，评委可引导团队回到本次评审内容。

## 5. 评分标准

### Challenge — 30 分

评审 **Change Log**，判断团队是否从 New Constraint Card 和其他团队的建议中理解、归纳并确定了一项或多项有意义的真实世界挑战。

对于每项优先挑战，清晰的挑战定义都应说明受影响的利益相关者、具体失效机制、可能造成的后果，以及可观察的预警信号。

| 分数 | 标准 |
| ---: | --- |
| 0-10 | 仅复制或罗列反馈，没有明确优先级或失效机制。 |
| 11-20 | 选择了一项或多项合理的挑战，但对利益相关者、后果或预警信号的说明仍不完整。 |
| 21-30 | 清楚归纳并确定了一项或多项具体、可信的挑战，且对每项优先挑战都说明了相关利益方、后果和预警信号。 |

### Fix — 45 分

评审 **Change Log** 和 **Final Demo**。

有效的 Fix 应对工作流程、产品逻辑、监测、权限、沟通、可及性、升级处理或暂停/终止机制做出实质性改变。仅优化视觉效果或增加页面，不构成有效的 Fix。

| 分数 | 标准 |
| ---: | --- |
| 0-15 | 没有作出实质性回应，或仅进行了与优先挑战关联很弱的表面修改。 |
| 16-30 | Demo 中能够看到相关修改，但其理由、实现、测试或取舍仍不完整。 |
| 31-45 | 作出了实质、连贯且可测试的重新设计，直接回应优先挑战，并说明了关键取舍。 |

### World Readiness — 25 分

评审 **Final Demo** 以及团队对预期使用情境的说明。

评委应考虑最终设计是否具备清晰的工作流程，是否顾及用户及虽非用户但会受其影响的人群，是否正视实际限制与重要的不确定性，以及是否设置适当的监测和暂停/终止条件。

| 分数 | 标准 |
| ---: | --- |
| 0-8 | 缺乏可行的真实世界应用路径或责任边界，且忽视重大风险。 |
| 9-17 | 具备基本可行的方案，但对重要用户、限制条件、监测机制或不确定性的考虑仍不充分。 |
| 18-25 | 设计可信、包容且符合实际运行条件，明确说明了边界、监测、升级响应和暂停/终止条件。 |

## 6. 评分表使用方法

1. 根据团队编号和名称找到对应行。
2. 确认团队参加的是 PROJECT TRACK 还是 SCENARIO TRACK。
3. 分别填写 Challenge、Fix 和 World Readiness 三项得分。
4. 将三项分数相加，得到满分 100 分的总分。
5. 在第二行写下一条简短、可执行的评审意见。

评语应指出最有效的一项设计决策，或下一步最需要改进的一项内容。请避免使用“展示得很好”或“项目很有趣”等笼统评价。

## 7. 评审原则

- 不评审 Baseline Demo。
- 不因生物学新颖性或项目成熟度本身而加分。
- 除非展示效果确实改善了项目在真实世界中的沟通或使用，否则不因展示精美而加分。
- 根据团队实际展示和说明的内容评分，不为团队承诺未来完成的内容加分。
- 对两个赛道采用相同标准。
- 不因挑战听起来严重或戏剧化而加分；应根据挑战是否可信、有用进行评价。
- 不应鼓励可能直接导致生物危害的具体技术建议。
- 如与参赛团队存在利益冲突，应在评分前向主办方申报。

## 8. 同分处理

如两支团队总分相同，依次比较以下项目：

1. **Fix** 得分较高者优先。
2. **Challenge** 得分较高者优先。
3. **World Readiness** 得分较高者优先。
4. 如仍然同分，由评委讨论哪支团队更清楚地展示了从证据到设计决策的推理过程。

## 9. 最后提醒

WORLDPROOF 以对抗为方法，以协作为目标。我们鼓励团队主动暴露关键假设、正面回应批评，并据此改进面向真实世界的设计。

感谢您投入时间并提出宝贵意见！您的专业判断和建设性反馈，不仅保障了 WORLDPROOF 的评审质量，也将帮助参赛团队把现场修改转化为下一轮更扎实的迭代。
